# 调用方 AI 使用说明

本文供负责“读取追踪热点、从外部来源采集热点信息、生成 AI 总结并回传”的调用方 AI 或自动化程序使用。

本文的章节组织参考 [price-monitor 的调用方 AI 使用说明](https://github.com/wahbm/price-monitor/blob/main/docs/caller-ai-guide.md)，接口、字段和行为以本项目实际契约为准。

调用方不是管理后台管理员。它不登录网页、不读取企业微信机器人 key，也不访问管理员接口；它只使用管理员分配的 API key 调用两个版本化接口：

- `GET /api/v1/topics`：读取当前启用的追踪热点及管理员备注；
- `POST /api/v1/articles`：提交一条热点信息。

采集来源、定时调度和 AI 总结由调用方自行完成。后台只保存调用方提交的内容，并为匹配的订阅方创建通知任务。

## 1. 管理员先完成配置

管理员需要在后台完成以下步骤：

1. 创建调用方，填写一个便于识别的名称。
2. 创建后立即复制页面显示的 API key，并通过安全的密钥交接方式交给调用方。
3. 需要停用调用方时禁用它；怀疑 key 泄露时重置 key，并把新 key 安全交给调用方。

完整 key 只在创建或重置时显示，数据库只保存摘要。重置或禁用后，旧 key 立即不能使用。调用方不需要也不应该知道管理员账号、管理员会话或订阅方的企业微信 key。

## 2. 地址与认证

生产环境地址示例：

```bash
export BASE_URL='https://8.130.116.192/davyluiy/fetch-news'
export API_BASE="$BASE_URL/api/v1"
```

部署到其他域名或公共子路径时，只替换 `BASE_URL`；不要把 `/api/v1` 重复拼接。接口文档地址是 `$BASE_URL/api/docs/`，仅管理员登录后可查看，不是调用方的运行依赖。

每个请求都必须使用 HTTPS 和 Bearer key：

```http
Authorization: Bearer <CALLER_KEY>
Content-Type: application/json
```

调用方应校验证书，不要使用 `curl -k` 或关闭 TLS 校验。建议把 key 放入密钥管理服务或受保护的环境变量中，不要写入代码仓库、提示词、普通数据库、请求日志、异常详情或模型输出。

## 3. 启动时读取热点配置

调用方启动和重启时应先完整读取启用热点列表，并以热点 `id` 作为任务主键：

```bash
curl --fail-with-body "$API_BASE/topics?page=1&pageSize=100" \
  -H "Authorization: Bearer $CALLER_KEY"
```

响应示例：

```json
{
  "items": [
    {
      "id": 1,
      "name": "web3",
      "note": "只查看 Ethereum 网络的热点",
      "createdAt": "2026-09-13 08:00:00.000",
      "updatedAt": "2026-09-13 08:00:00.000"
    }
  ],
  "total": 1,
  "page": 1,
  "pageSize": 100
}
```

分页规则如下：

- `page` 从 `1` 开始；`pageSize` 为 `1–100`，建议使用 `100` 减少请求次数；
- 当 `page * pageSize >= total` 时读取完成，否则递增 `page`；
- 只返回启用热点，停用热点不会出现在新列表中；
- `id` 是稳定身份，`name` 只是展示名称，不要用名称作为唯一键；
- `note` 是管理员给采集任务的额外约束，例如地域、网络、行业或关键词范围。采集时必须遵守；备注为空表示没有额外限制；
- 服务端没有提供 `updatedSince`、ETag 或 `nextCursor`。调用方需要自行定期全量同步，并移除本地已经不在启用列表中的任务；
- 后台不规定调用方的定时周期。请根据来源限制和业务时效安排周期，并遵守接口限流。

热点停用会保留历史信息。停用后不能新增信息，但此前已经保存的记录仍可在管理后台查询。

## 4. 采集和整理原则

调用方负责访问自己的信息来源。不要把来源网站的 Cookie、登录 token、账号密码、完整页面 HTML 或其他无关隐私发送给管理后台；回传只需要提交规定字段。

每条来源信息整理为一条独立记录：

- `date` 填写事件或文章的真实日历日期，不要把抓取时间误当成事件日期；无法确认日期时，应根据来源标注或业务规则处理，不要静默编造；
- `title` 使用准确、可搜索的标题，去掉首尾空白，避免把整段正文当标题；
- `aiSummary` 给出基于来源内容的简洁总结，可以为空。不要把推测、未经来源支持的结论写成事实；
- `content` 保存可供后台检索和复核的纯文本正文或关键事实，去除 HTML 标签和脚本，不要夹带提示词、凭据或无关页面代码；
- `url` 使用能直接打开原文的 HTTP/HTTPS 地址。服务端不会抓取、验证或跟随该链接，因此调用方应在提交前确认链接可用；
- 同一来源页面若对应多个不同热点，可以按不同 `topicId` 分别提交；同一热点下不要重复提交同一个链接。

建议在提交前做一次本地检查：热点 ID 仍在最近一次启用列表中、日期格式正确、标题和正文非空、URL 不含账号密码、摘要与正文没有秘密信息。

## 5. 提交热点信息

接口：

```http
POST /api/v1/articles
```

最小请求示例：

```bash
curl --fail-with-body "$API_BASE/articles" \
  -H "Authorization: Bearer $CALLER_KEY" \
  -H 'Content-Type: application/json' \
  --data-binary @- <<'JSON'
{
  "topicId": 1,
  "date": "2026-09-14",
  "title": "Ethereum 网络出现新的协议动态",
  "aiSummary": "来源显示……",
  "content": "保留用于后台搜索和复核的纯文本内容。",
  "url": "https://example.com/news/ethereum#section"
}
JSON
```

字段约束：

| 字段 | 要求 |
| --- | --- |
| `topicId` | 必填正整数，必须对应热点；使用最近同步得到的 `id`。 |
| `date` | 必填，真实日历日期，格式为 `YYYY-MM-DD`；日期必须有效。 |
| `title` | 必填字符串，服务端去首尾空白，最多 500 个字符。 |
| `aiSummary` | 可省略，默认空字符串，最多 12,000 个字符；允许为空。 |
| `content` | 必填纯文本，服务端去首尾空白，最多 200,000 个字符。 |
| `url` | 必填 HTTP/HTTPS 地址，最多 2,048 个字符；不能含内嵌账号密码。 |

### URL 规范化与去重

服务端会使用标准 URL 解析器规范化链接：统一协议和主机的表示、去除默认端口、移除 fragment（例如 `#section`），保留路径和查询参数，不自动排序或删除查询参数，也不解析重定向。括号会进行百分号编码。规范化后仍要求不超过 2,048 个 UTF-8 字节。

唯一性由“热点 ID + 规范化 URL 摘要”决定：

- 同一热点重复提交相同规范化 URL：返回已有记录 ID，不覆盖原来的标题、总结或正文，也不会再次创建通知任务；
- 不同热点可以保存同一个 URL，各自形成独立记录；
- 并发重复提交也按同一规则处理；
- 网络超时后可以安全重试原请求，必须保留原 `topicId`、内容和 URL，让服务端返回 `duplicate: true`，不要为了重试改写 URL 或内容。

首次写入：

```http
201 Created
```

```json
{"id": 42, "duplicate": false}
```

重复写入：

```http
200 OK
```

```json
{"id": 42, "duplicate": true}
```

`201` 或 `200 + duplicate:true` 都表示该条任务已经可以结束。入库成功只代表后台已持久化，不代表企业微信已经送达。

## 6. 通知行为

新信息和通知任务在同一个数据库事务中写入。提交成功后，后台会为提交时处于启用状态且匹配该热点的每个订阅方创建一条任务：

- 订阅“全部热点”的订阅方自动匹配当前和未来新增热点；
- 指定热点的订阅方只匹配所选热点；
- 修改订阅范围不会补发历史信息；
- 重复提交不会再次通知；
- 调用方不发送企业微信消息，也不能读取 webhook key；
- 未配置订阅方、通知暂时失败或通知方被禁用，都不影响信息本身的保存。

后台 worker 会异步发送 Markdown 通知，并记录等待、成功、失败和每次尝试。调用方无需等待通知结果，也不要因为通知失败重复提交文章。

## 7. 错误处理和重试

错误响应统一为：

```json
{"message": "错误说明"}
```

常见状态码：

| HTTP 状态 | 含义 | 调用方动作 |
| --- | --- | --- |
| `400` | 字段、日期、URL 或请求格式无效 | 修正请求后再提交，不要盲目重试。 |
| `401` | key 缺失、错误、已重置或调用方已禁用 | 停止调用并联系管理员，不要无限重试。 |
| `404` | `topicId` 不存在 | 重新读取热点列表；不要创建热点。 |
| `409` | 热点已停用，或其他唯一约束冲突 | 若是停用热点，重新同步并停止该任务；若请求可能已成功，先按原内容重试一次确认是否返回重复。 |
| `413` | 请求体超过 1 MiB | 缩短正文或拆成多条有明确来源的记录；不要提交超大 HTML。 |
| `429` | 当前 key 触发限流 | 遵守 `Retry-After`（如果返回），使用退避后再试。 |
| `500` | 服务端或数据库暂时故障 | 有限次指数退避，重试时复用完全相同的请求。 |

调用方接口按每个 key、每个接口默认最多 120 次/分钟；请求体上限为 1 MiB。建议退避时间为 1、2、5、10、30 秒并设置总重试上限。对 `400`、`401`、明确的 `404` 和已确认的 `409` 不要无限重试。

如果请求在网络层超时，无法判断服务器是否已写入：

1. 不要生成新的“重试 ID”（本 API 没有单独的客户端观测 ID）；
2. 使用原始 JSON 再试一次；
3. 收到 `200 + duplicate:true` 时按成功处理；
4. 仍失败时记录本地脱敏日志和 HTTP 状态，稍后按退避恢复。

## 8. 推荐执行循环

```text
启动或恢复
  ├─ 读取 GET /topics 的全部分页
  ├─ 建立 topicId → name/note 的本地缓存
  ├─ 移除已停用或不再返回的本地采集任务
  └─ 保存上次同步时间（仅供调用方调度使用）

每个任务周期
  ├─ 读取热点 name 和 note，按备注约束选择来源
  ├─ 访问外部来源并确认标题、事件日期、正文和原文链接
  ├─ 生成基于来源的 aiSummary，不猜测缺失事实
  ├─ 通过 POST /articles 提交纯文本信息
  ├─ 201 或 duplicate=true → 标记成功
  ├─ 400/404/已确认的 409 → 修正或移除任务
  └─ 429/5xx/网络超时 → 限次退避，原请求安全重试

重启或网络恢复
  ├─ 重新分页读取启用热点
  ├─ 恢复未完成任务，不使用旧内容冒充新的日期记录
  └─ 不输出或上传 API key、Cookie、token、原始 HTML
```

## 9. 最小验收清单

- 能用管理员分配的 key 读取 `GET /topics`，并处理所有分页；
- 采集任务使用 `topicId`，每次遵守对应热点的 `note`；
- 日期、标题、摘要、正文和 URL 符合字段限制；
- URL 不含账号密码，提交前能确认原文地址；
- 新信息收到 `201`，重复信息收到 `200` 且 `duplicate:true` 时都不再生成本地重复任务；
- 网络超时或 `5xx` 重试时复用原始请求，不伪造新内容；
- 收到 `401` 后停止并联系管理员，收到 `429` 或 `5xx` 时限次退避；
- 本地日志和模型上下文中没有 API key、来源 Cookie、token、密码或完整 HTML；
- 不尝试访问管理员 API、OpenAPI 管理页面或企业微信 webhook。

管理员和开发者可参阅 [调用方 API](./API.md) 获取简版 curl 示例和完整状态码说明。
